# Market indices (migrations 128 + 130)

*Moved out of CLAUDE.md on 2026-09-30; CLAUDE.md keeps the pointer and the rules that bite.*

`market_index_daily` + `market_index_latest`, scoped `all` / `set:<id>` / `rarity:<r>`. A **chain-linked, equal-weighted RETURN index** rebased to 100 — deliberately NOT Card Ladder's CL50 price-sum (original Dow) shape, which lets the priciest component dominate so one $900 Enchanted would drown four thousand commons. Chaining is what makes a growing catalog safe: a card first priced in month 8 contributes from month 8 and never creates a phantom jump on arrival.

Four guards, all because raw TCGCSV is noisy: **`market_price` first** (low_price is a sticker, not a sale); **MAX_GAP_DAYS** (`lag()` returns the previous ROW, not DAY — a 40-day hole would otherwise hand its 40-day move to one day); **winsorized, not discarded** returns (discarding biases the index up on crash days, when extremes skew negative); **MIN_COMPONENTS** (a day computed from three cards is noise in an index's clothes; below the floor the day drops, which on a chained series holds the level rather than inventing a move).

- **The ETL refresh is OPTIONAL and must stay that way.** Every other matview there is load-bearing for a displayed price; a stale benchmark costs a column for a day. It is also the slowest refresh on the site, so failing the ETL over it trains us to ignore its alerts. `statement_timeout` is pinned per the migration-109 lesson.
- **Scopes (130): `all` · `set` · `rarity` · `setrarity` · `chase` · `ink` · `sealed` · `sealedtype`.** `setrarity:<set_id>|<rarity>` is "this set's Enchanteds". Sealed is its OWN universe, never folded into `all` — a booster box and a single are different assets with different buyers, and averaging them describes neither.
- **⚠ The day-qualifying floor is COVERAGE, not a count.** 128 kept a day only if ≥20 cards contributed, which is right for a wide scope and wrong for a narrow one: a set has ~12–18 Enchanteds and a handful of Iconics, so `setrarity` could never clear 20 and would have emitted an empty series **silently**. Verified against a live Postgres fixture: **0 of 796 days** survived the flat floor. 130 keeps a day when `n >= MIN_ABS (5)` AND `n >= 0.6 × (trailing 30-observation max n)` — the scope's own recent best coverage, so it self-calibrates to any width with no per-scope tuning and no extra join. Both directions verified: a 14-of-14 tier is kept, a 10%-coverage `all` day is dropped. `universe` ships alongside `n_components` so a thin index can be labelled honestly.
- **⚠ Every series is divided by its partition's own `first_value(cum)`, not just ×100.** A scope's first EMITTED day is already its second day with data (a return needs a prior observation), so multiplying the raw cumulative by 100 baked that day's return into the base and opened the series at 100.6 or 99.2. It hid well — a return near 1.0 rounds to 100, so only 32 of ~275 fixture series showed it. An index whose base is not its base makes every comparison against it wrong by a day-one wobble that never washes out.
- **⚠ Created WITH NO DATA, then populated via `select public.refresh_market_index();`.** `create materialized view` normally populates immediately, and that build runs under the SQL EDITOR's timeout, not the pin on the refresh function — which is how an expensive matview creation dies in the dashboard for reasons that look unrelated to the migration.
- **An index is a SUBJECT as well as a reference.** The `index` compare kind (Price Graphing → By Index) gives it a colour, a legend chip, a stats row, CSV and a share link, and lets several sit on one chart with no cards at all — "how did Enchanteds do against Commons" is a question about two subjects. The single dashed benchmark overlay stays a separate thing: a reference has no colour slot and no stats row. Index rows print points, never `$` — an index has no dollar value and inviting a reader to compare 119.7 against a card's price is a category error.
- **A CUSTOM index is any watchlist, computed in the browser** by `buildCustomIndex` — the server can't precompute one matview per user per basket. It MUST reproduce migration 130 exactly; two series both labelled "index" that compute differently destroys the only property a benchmark has. `scripts/test_market_index.mjs` checks it against a golden file captured from a real PostgreSQL run of 130's own CTE chain, over a fixture carrying a 10-day gap, a 9x spike and a participation collapse. `INDEX_PARAMS` is the contract — retuning one means a deliberate edit in both places, and the test pins the values.
  - One shared wart the test pins rather than hides: a coverage-dropped day is dropped from the AGGREGATE, not from the price series, so its observations still anchor the next day's return and a spike's reversal can leak in even though the spike didn't. Postgres does the same; verified. Fidelity beats being locally nicer.
  - A custom index travels in `?g=` as `w~<watchlistId>`, which only resolves for its owner. A shared link drops it and graphs the rest — the right degradation for a private basket, and better than freezing a snapshot of a list whose point is that it changes.
- **The Screener's vs column resolves its benchmark PER ROW** for the narrow bases (`vsMktBasis` ∈ all / set / rarity / setrarity). "Is this Enchanted beating the other Enchanteds from its own set" separates a card that is moving from a tier that is moving; "beating the whole market" does not. **No fallback to `all` on a miss** — a tier too small to index would otherwise show a number silently computed against a completely different universe, which is worse than a dash.
- Screener gets a default-hidden **vs Mkt** column following the active mover window; Price Graphing gets a benchmark picker. The benchmark rides along as a dashed muted series with a legend chip but **no colour slot and no stats row** — it is what you read the others against, not a ninth pick. Only meaningful against rebased lines, so picking one switches the chart to Indexed rather than drawing a flat line at the foot of a dollar chart.
